# MerchantIQ

Autonomous AI revenue intelligence and operations console that discovers hidden transaction friction, investigates root causes, and executes bounded recovery actions for online merchants.

---

## Problem

E-commerce merchants experience continuous revenue leakage from friction points that remain invisible in traditional dashboards:

- **Unnoticed Payment Failure Clusters**: Specific combinations of gateway, device OS, and transaction timing experience elevated failure rates without triggering global system alerts.
- **Silent Checkout Drop-Offs**: High-intent buyers abandon carts due to unoptimized payment routing, missing alternative payment methods, or friction in specific product verticals.
- **Concentrated Refund Spikes**: Subtle return spikes in specific categories or order value tiers drain margins before merchant operations identify the trend.
- **Price-Sensitive Conversion Losses**: Shoppers abandon transactions when rigid pricing models fail to accommodate reasonable negotiation thresholds.

Traditional merchant analytics tools only report aggregate historical metrics. By the time a merchant notices drop-offs in a monthly report, the revenue is already permanently lost.

---

## Solution

MerchantIQ provides an end-to-end autonomous revenue protection system:

1. Ingests raw merchant transaction data (or live exports from Shopify, Stripe, Razorpay, or custom ERPs).
2. Uncovers statistically significant friction patterns using unsupervised machine learning and contingency testing.
3. Quantifies the precise financial revenue at risk for each discovered problem.
4. Investigates the underlying operational root causes using evidence-grounded AI reasoning.
5. Recommends bounded, policy-controlled corrective actions through a deterministic decision engine.
6. Simulates safe resolution actions, enforces strict safety guardrails, and records outcomes in an autonomous impact ledger.

## Key Features

- **Merchant CSV Ingestion**: Upload transaction exports from any payment gateway, e-commerce platform, or database.
- **Automatic Column Alias Mapping**: Heuristic header normalization mapping arbitrary merchant column conventions into canonical schemas.
- **Transaction Normalization**: Robust parsing for monetary values, currency indicators, boolean flags, and multi-state status strings.
- **IsolationForest Anomaly Detection**: Unsupervised multivariate anomaly scoring across numerical and behavioral interaction features.
- **Statistical Subgroup Discovery**: Systematic segment enumeration across single, paired, and triplet dimensions with Chi-Square contingency testing ($p < 0.05$, relative change $\ge 2.0\times$, minimum segment volume $\ge 30$).
- **Revenue-at-Risk Calculation**: Opportunity-weighted financial quantification customized to problem types (payment failures, checkout drop-offs, refund surges).
- **AI Root-Cause Investigation**: Evidence-grounded causal hypotheses generated by Google Gemini 1.5 Flash using structured statistical metrics rather than raw private data.
- **Deterministic Decision Engine**: Strict safety rules guaranteeing that high-risk actions (e.g., refunds) require human approval and only low-risk actions can proceed autonomously.
- **Safe Resolution & Dry-Run Execution**: Simulation environment executing bounded interventions (`payment_recovery`, `bargainai_offer`, `conversion_recovery`, `refund_review`, `monitor`) without unverified mutations.
- **Closed-Loop Outcome Tracking**: Live dashboard telemetry tracking recovery efficiency, resolution progress, and activity audit trails.

## AI Architecture

MerchantIQ separates statistical discovery, causal reasoning, and financial execution into discrete, bounded layers:

```
┌─────────────────────────────────────────────────────────────┐
│                    STATISTICAL LAYER                        │
│  - IsolationForest (Contamination = 0.08)                   │
│  - Chi-Square Contingency Tests (p < 0.05)                  │
│  - Segment Grid Search across Dimensions & Buckets          │
│  * Deterministic, Mathematical, No Hallucinations           │
└──────────────────────────────┬──────────────────────────────┘
                               │ Structured Evidence
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                    REASONING LAYER                          │
│  - Google Gemini 1.5 Flash                                  │
│  - Ingests Aggregated Evidence Bullets (No Raw PII / CSV)   │
│  - Generates Root-Cause Hypotheses & Action Recommendations │
│  - Deterministic Rule-Based Fallback if LLM is Unavailable  │
└──────────────────────────────┬──────────────────────────────┘
                               │ Validated Pydantic Schema
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                    DECISION LAYER                           │
│  - Hardcoded Risk Matrix (LOW / MEDIUM / HIGH)              │
│  - Automation Guardrails (automation_allowed only for LOW)  │
│  - Human-in-the-Loop Approval for High-Risk Actions         │
│  * The LLM Never Executes Financial Actions Directly        │
└─────────────────────────────────────────────────────────────┘
```

1. **Statistical Engine**: Discovers patterns strictly using Scikit-Learn and SciPy. No generative AI is used in the discovery phase, eliminating hallucinations in statistical detection.
2. **Investigation Engine**: Gemini receives structured evidence summaries (e.g., segment failure rate, baseline failure rate, relative change, p-value, sample size) to infer operational context. If the LLM is unreachable or unconfigured, the system automatically defaults to a deterministic diagnostic fallback.
3. **Decision & Safety Engine**: Hard-coded Python logic enforces policy boundaries. An LLM can recommend an action, but the decision engine dictates whether automation is permitted. Financial actions like refunds or payment reversals are permanently categorized as high risk and cannot be automated.

## Merchant CSV Analysis

The ingestion pipeline maps diverse merchant export schemas into canonical dimensions:

| Canonical Field | Detected Aliases (Case-Insensitive) | Description |
| :--- | :--- | :--- |
| `amount` | `total`, `price`, `transaction_amount`, `order_amount`, `order_value`, `value`, `net_amount`, `gross_amount`, `amt`, `cost` | Transaction gross value, sanitized of currency symbols (₹, $, commas). |
| `payment_status` | `status`, `payment_state`, `transaction_status`, `txn_status`, `state`, `charge_status`, `result` | Normalized to `SUCCESS`, `FAILED`, or `PENDING`. |
| `payment_method` | `method`, `payment_mode`, `mode`, `payment_type`, `gateway`, `pay_mode`, `channel` | Payment instrument (Card, UPI, NetBanking, EMI, Wallet). |
| `device_type` | `device`, `platform`, `os`, `client_type`, `device_category`, `client` | Operating platform (Android, iOS, Web). |
| `product_category` | `category`, `item_category`, `product_type`, `department`, `vertical` | Merchant vertical or product line. |
| `location` | `city`, `region`, `state`, `country`, `geo`, `zone`, `shipping_city` | Geographic cluster. |
| `cart_abandoned` | `checkout_status`, `cart_status`, `abandoned`, `cart_dropped`, `is_abandoned`, `cart_state` | Evaluates boolean flags and status values (`abandoned`, `dropped`, `incomplete`). |
| `refund_requested` | `refund_status`, `refunded`, `is_refund`, `refund_flag`, `return_status`, `refund_state` | Evaluates boolean flags and refund statuses (`refunded`, `requested`, `returned`). |

If a column matches multiple alias patterns, higher-priority operational fields claim the header first to prevent ambiguous double-mapping.

## Razorpay Integration

MerchantIQ integrates with Razorpay Test Mode:

- **Order Creation (`/payments/create-order`)**: Calls Razorpay Orders API to generate an authenticated order with exact paise calculation, receipt ID, and merchant metadata notes.
- **Cryptographic Webhook Verification (`/payments/webhook`)**: Validates inbound webhook events (`payment.captured`, `order.paid`, `payment.failed`) against `RAZORPAY_WEBHOOK_SECRET` using constant-time HMAC-SHA256 comparison.
- **Idempotency Safeguards**: Verifies webhook event IDs and transaction states against SQLite audit logs to ensure duplicate webhook payloads cannot trigger repeated ledger updates.
- **BargainAI Deal Completion**: Connects approved negotiated deals into Razorpay checkout orders, transitioning bargains to completed status upon verified webhook receipt.

*Note: In the current version, autonomous recovery routing actions operate in a simulated dry-run mode. Live payment flows in this repository run against the official Razorpay Test Mode API for order generation and verification.*

## Safety & Limitations

- **Dry-Run Simulation**: Autonomous resolution actions execute within a dry-run execution harness (`action_executor.py`). Actions return `status: "simulated"` and do not mutate production gateway routing or trigger external financial calls.
- **Modeled Revenue Estimates**: Estimated revenue at risk and recovered revenue figures represent modeled statistical recovery potential based on standard conversion assumptions (65% recoverable failed payments, 40% cart recovery potential, 30% low conversion recapture). They are decision-support projections, not realized balance sheet gains.
- **Benchmark Synthetic Dataset**: Default demo operations use a 10,000-event synthetic dataset (`backend/data/merchant_events.csv`) designed to benchmark discovery of multi-dimensional transaction anomalies. Custom CSV datasets can be uploaded and analyzed live through the dashboard.
- **Safety Guardrails**: High-risk financial interventions (refunds, transfers, cancellations) have hardcoded `automation_allowed: False` constraints and strictly require merchant review.

## Local Setup

### Prerequisites
- Python 3.10 or higher
- Node.js 18 or higher (with npm)
- Git

### 1. Clone the Repository
```bash
git clone https://github.com/Jaanvimutreja/MerchantIQ.git
cd MerchantIQ
```

### 2. Backend Setup
```bash
# Navigate to backend directory
cd backend

# Create and activate virtual environment
python -m venv venv

# Windows (PowerShell)
.\venv\Scripts\Activate.ps1
# macOS/Linux
# source venv/bin/activate

# Install dependencies
pip install -r requirements.txt

# (Optional) Configure environment variables
# Create a .env file in backend/ with:
# GEMINI_API_KEY=your_gemini_api_key_here
# RAZORPAY_KEY_ID=rzp_test_your_key_id
# RAZORPAY_KEY_SECRET=your_key_secret
# RAZORPAY_WEBHOOK_SECRET=your_webhook_secret

# Start backend server
python -m uvicorn main:app --host 127.0.0.1 --port 8000
```
Backend will be available at `http://127.0.0.1:8000`. Interactive OpenAPI documentation is accessible at `http://127.0.0.1:8000/docs`.

### 3. Frontend Setup
```bash
# In a separate terminal, navigate to frontend directory
cd frontend

# Install dependencies
npm install

# Start Next.js development server
npm run dev
```
Frontend dashboard will be available at `http://localhost:3000`.

### 4. Running Tests
```bash
# Run from repository root with backend virtual environment active
.\backend\venv\Scripts\python.exe -m pytest backend/tests/ -v
```
